Rolling interview Q&A, updated every session — grounded in what was actually built/decided.

## Session 1 — 2026-08-28

**Q: Why did you use the GPT-2 tokenizer instead of training your own on WikiText-103?**
A: The thing under test in this project is the routing/adaptive-depth mechanism, not tokenization quality. Training a custom BPE tokenizer would introduce a second uncontrolled variable — I wanted vocabulary and tokenization held constant so any difference in the accuracy-vs-depth curve is attributable to the router, not to how the text was chunked.

**Q: Why 12 layers for the baseline instead of something smaller or larger?**
A: It's a balance between two constraints: the router needs enough depth to have a meaningful range of early/mid/late exit points to learn over (a 2-3 layer model wouldn't show an interesting curve), and training time has to fit a free-tier Colab/Kaggle T4 GPU. 12 layers / d_model=384 (~15M params) was chosen as the smallest size likely to produce a non-trivial depth-vs-accuracy tradeoff.

**Q: Why not use Hugging Face's `Trainer` for the training loop?**
A: Two reasons: the project's stated goal is understanding, not just output, so the loop is hand-written; and later, the adaptive-depth training loop needs custom per-token masking/routing logic during the forward and backward pass that `Trainer` doesn't cleanly support — better to have full control from the start rather than fight the abstraction later.

**Q: How do you know the training loop actually works before spending your free GPU quota on a full run?**
A: Two layers of verification, cheapest first. Locally (no GPU): a smoke test with a tiny random config (2 layers, d_model=32) checks the forward pass shape, that the loss is finite, that backward produces no NaN gradients, and that `generate()` runs — pure code-correctness, no claim about model quality. Then in Colab, before the real run, a 200-step "smoke run" on the actual GPU with the real data pipeline confirms training loss actually decreases end-to-end. Only after both pass does the full run start — this catches bugs cheaply instead of discovering them 15,000 steps into a real run.

**Q: Why does the Colab notebook write out the source files with `%%writefile` instead of `git clone`-ing the repo?**
A: There's no GitHub remote for this project yet (and Claude Code has no push authority by default), so the notebook has to be self-contained. The files are generated into `%%writefile` cells programmatically from the actual reviewed `src/` files (not retyped by hand), so the code Colab runs is guaranteed identical to what's in the repo.

## Session 2 — 2026-08-29

**Q: Why does this project matter outside of getting a model to train — what's the actual business case?**
A: Every production LLM call costs GPU-seconds proportional to tokens × layers, paid regardless of whether a given token actually needed that much computation. At the scale companies serve traffic, even a modest average-compute-per-token reduction is real money, lower latency, and less energy — which is exactly why DeepMind (Mixture-of-Depths) and Google (CALM) are actively researching this. This project is a from-scratch, hands-on demonstration of understanding and attacking that specific, universal cost problem — not a novel deployable product.

**Q: You found a bug where the data cache path was wrong on Colab but correct locally — what caused that, and what's the general lesson?**
A: `data.py` computed its cache directory relative to `os.path.dirname(__file__)`, assuming the file always sits inside a `src/` folder with a sibling `data/` directory one level up — true for the local repo, but false in Colab, where the notebook writes all files flat into `/content` with no `src/` subfolder. The same `../data/tokenized` relative path then walks one directory too far up, landing outside the working directory entirely. The general lesson: `__file__`-relative paths silently encode an assumption about directory layout; when the same code needs to run in more than one layout (local repo vs. a flattened Colab environment), it's safer to resolve paths from `os.getcwd()` or take them as an explicit parameter instead.

## Session 3 — 2026-08-30

**Q: You hit an `HfUriError` loading WikiText from Hugging Face — what actually broke, and why didn't it break earlier?**
A: The Hugging Face Hub deprecated bare, namespace-less repo ids for script-based dataset loaders — `load_dataset("wikitext", ...)` used to resolve directly, but the Hub now requires the canonical `"namespace/name"` form, `"Salesforce/wikitext"`. Nothing in our code changed; the external service's resolution rules did. It's a reminder that pinning a dataset/model id isn't enough for long-term reproducibility — the *hosting platform's* addressing scheme can shift under you, so before trusting a remembered id it's worth checking the live Hub page rather than assuming.

**Q: The `results_dir = "../results"` bug looks identical to the `CACHE_DIR` bug from last session — why did it take a second pass to catch?**
A: Because it's the same root-cause bug *class* (a `..`-relative path that assumes a specific directory layout) but a different instance, in a different file, that wasn't touched during the first fix. Fixing one occurrence of a pattern doesn't guarantee every occurrence is fixed — after the second one surfaced, I did a full repo sweep for the same pattern (`..`-relative and `__file__`-relative paths) rather than just patching the reported line, and found a third spot (`train.py`'s git-commit lookup) that turned out to already be safe. General lesson: once a bug class is identified, grep for the whole class across the repo, not just the one instance that got reported.

**Q: You found a third instance of that same relative-path pattern but chose not to fix it — why?**
A: `train.py`'s `get_git_commit()` runs `git rev-parse HEAD` with `cwd=os.path.dirname(__file__)`, which resolves to `/content` in Colab — not a git repo, so the call fails. But it's wrapped in `try/except Exception: return "unknown"`, so the failure mode is a placeholder string in `config.json`, not a misplaced file or silent data corruption. Since Colab never actually clones the repo, `"unknown"` is the *correct* value there, not a symptom of a bug — fixing it would add complexity for a case that isn't actually broken. The lesson: the same code pattern isn't automatically the same severity of bug everywhere it appears — check whether a given instance is silently wrong (needs fixing) or fails safe (may not).

## Session 4 — 2026-08-30

**Q: How does a token actually "skip" a layer in your adaptive model — walk me through the mechanism.**
A: Each `AdaptiveBlock` wraps the same `Block` used in the baseline (attention + MLP), plus a per-token router. The router looks at the block's input and outputs a gate in (0,1). The block's output is then blended with its input using that gate: `x_new = gate * block(x) + (1 - gate) * x` — a highway-network-style blend. Gate near 1 applies the block in full; gate near 0 leaves the token essentially untouched, so its representation just passes through unchanged. Right now (Phase 1) every token still runs through the full block every layer — nothing is actually skipped compute-wise yet, only down-weighted — because that keeps the whole thing differentiable by ordinary backprop, no REINFORCE or straight-through estimator needed. Real hard skipping (actual FLOPs savings via token compaction) is a deliberately separate, later phase, so routing behavior can be validated on its own first.

**Q: Why does the router start biased toward "keep going" instead of a neutral 50/50, and what did testing that reveal?**
A: The router's last layer is zero-initialized with a bias so it starts at gate ≈ 0.88 for every token, regardless of the (still-random, untrained) hidden state it's fed. At step 0 the base transformer hasn't learned anything, so router decisions would otherwise be arbitrary — starting near "always continue" avoids randomly freezing tokens before there's any real signal to route on. Testing this turned up something non-obvious: because the last layer's weight is exactly zero, the gradient flowing *back into the hidden state* is also exactly zero on the very first backward pass — the zero weight matrix blocks the chain rule. The router's own weight still gets a valid gradient, though, since that only depends on the activations feeding it, not on the weight's current value — so the router bootstraps itself off zero on the first optimizer step, and only after that does gradient start flowing back into the base model too. That's expected behavior, not a bug, but my first draft of the test asserted the opposite and had to be corrected once I traced through the actual chain rule.

**Q: You added a compute-budget loss term — why is the LM loss alone not enough, and what does the budget loss actually penalize?**
A: Cross-entropy alone never penalizes using more layers — more compute is never wrong for next-token prediction, so nothing pushes the model toward using fewer. The budget loss adds a quadratic penalty pulling the batch's *average* effective depth (each token's gates summed across layers, averaged over the batch) toward a target value. The important detail is that it penalizes the batch average, not each individual token's depth — a per-token penalty would push every token toward the same depth, which directly fights the project's whole premise that depth should vary a lot by token difficulty. An average-depth penalty only constrains the aggregate compute budget and leaves per-token routing completely free to be as heterogeneous as the data calls for. Training separate runs at different target values is how the accuracy-vs-average-layers curve — the project's central result — actually gets built.

**Q: You said you verified the router's gradients — what does "verified" actually mean here, versus just "the code ran without erroring"?**
A: A few concrete things, not just no-crash: checked the *exact numeric value* of average depth at initialization against a hand-computed expectation (0.88 × number of layers) rather than just checking it was some finite number — that's what caught a real bug where the model's blanket weight-init pass was silently re-zeroing every router's carefully-set bias, undoing the bootstrap trick. Checked gradient *sign*, not just non-zero-ness, for the budget loss (does it actually push depth down when above target, and up when below). And for both the budget loss and the training script, ran a real integration test — actual optimizer steps on a tiny model — and confirmed the measured average depth moved in the intended direction, rather than just trusting that non-zero gradients imply correct behavior.

**Q: Your model.py already had a `BaselineTransformer` class working and validated — how did you avoid breaking it while adding the adaptive model to the same file?**
A: Two things. First, a scoping decision: `AdaptiveTransformer` duplicates `BaselineTransformer`'s embedding/init/weight-tying boilerplate rather than refactoring both to share a base class — a few similar lines is a smaller risk than touching the already-validated baseline's class structure for the sake of DRY-ing it up mid-task. Second, verification: after editing the shared file, I reran the original baseline smoke test (forward/backward/generate shape and gradient checks) to explicitly confirm zero behavior change, rather than assuming the new code was purely additive just because it was in a new class.

## Session 5 — 2026-09-01

**Q: You added periodic checkpointing to survive a mid-run disconnect — but wasn't training already checkpointing periodically? What was the actual gap?**
A: Yes — the training loop was already saving `ckpt.pt` every `eval_interval` steps, well before this session, and at the default setting (500 steps) that's actually *more* frequent than what was being asked for. The real gap wasn't "no periodic saving exists," it was that checkpoint cadence was welded to eval cadence — and eval is expensive (real forward passes over many batches, both splits), while a checkpoint save is just a cheap state-dict dump. If you widen `eval_interval` on a long run to cut down on that overhead, checkpoint safety silently degrades right along with it, with no separate knob to compensate. I decoupled them with a `ckpt_interval` config field that defaults to matching `eval_interval` (so nothing changes unless you explicitly ask), and proved the decoupling was real — not just present in the code — by configuring `eval_interval` wide enough to never fire again after step 0, and confirming a checkpoint still landed on disk on its own independent cadence.

**Q: You built a whole new Colab notebook for the adaptive model — how did you make sure it actually reproduces the real source files, not just something that looks similar?**
A: Every `%%writefile` cell is generated by reading the actual `src/*.py` file and embedding its exact content — verified byte-for-byte identical to the source afterward, not just eyeballed. But I went a step further this time: I wrote all six cells' bodies out to a real flat directory with no `src/` subfolder — exactly how Colab's filesystem will actually look after running the notebook — and ran the notebook's own import sequence against that flat layout, then actually called `train()` end-to-end from there with fake data standing in for the real dataset download. Byte-identity alone wouldn't have caught an import-order problem that only shows up once the files are genuinely flat instead of nested; actually simulating the target environment does.

**Q: The first real training attempt on real data stopped partway through — what did you actually learn from that, versus just "it broke"?**
A: Two things, and they're different in kind. First, a genuinely positive result: up to step 3000, `avg_depth` was measurably converging toward the target and loss was decreasing — the first time the router mechanism had been validated on real language data instead of random tokens, where there's no actual signal for the LM loss to compete against the budget loss with. That's meaningfully stronger evidence than anything from the earlier smoke tests. Second, a platform lesson: I'd designed the mid-run checkpoint safety net around Colab's recovery model (a file you can grab from a live, always-downloadable panel at any point), and Kaggle's actual persistence rules are different enough — an interactive session loses everything in `/kaggle/working` on disconnect, and even Kaggle's own recommended "run in the background" mode doesn't reliably capture output if the notebook actually crashes rather than completing cleanly — that the fix doesn't fully transfer without re-checking it against the specific platform it's actually running on.

**Q: Looking back, what would you check before spending another multi-hour run, given this one stopped for an unconfirmed reason?**
A: Kaggle's own Versions/Output tab for that specific run — it should show whatever status Kaggle itself recorded (crashed, stopped, still whatever state it was in) far more reliably than reasoning about it after the fact from a local wifi disconnect theory. I did find decent secondhand evidence that a genuinely-committed background job shouldn't be affected by local wifi or a closed tab at all (it's described as non-interactive and exempt from the inactivity timeout that kills live sessions), which actually points *away* from wifi as the cause and toward either a manual stop or an actual kernel-level crash — but I couldn't get a fully authoritative, first-party source confirming that, so I logged it as the first thing to verify before retrying rather than assuming it and moving on.

**Q: You now have two points toward the accuracy-vs-avg-layers curve — what do they actually show, and what can't you claim yet?**
A: Going from an average of 6.08 layers down to 2.65 — less than half the compute — only cost 0.08 in val LM loss (3.8135 to 3.8915). That's a genuinely striking early result for the project's core premise: most tokens really don't need the full depth. What I can't claim yet is the *shape* of that tradeoff — with only 2 points I can't tell whether it degrades this gently everywhere down to very shallow depths, or whether there's a cliff somewhere below 2-3 layers where quality collapses. That's exactly why the sweep needs the remaining points (4 and 9), not just more confirmation of the same two.

**Q: Why did the curve-plotting script need to be a separate piece of code rather than an extension of the existing training/plotting logic?**

The actual central-result curve is across runs — one point per completed run, comparing final quality against final compute after training is done. Trying to bolt that onto the per-run training loop would conflate two things that should stay separable: whether one run trained correctly, and how a family of runs compares to each other.

**Q: How did you verify `plot_curve.py` would correctly handle the real sweep, given only one run existed when you first built it?**

So I built a synthetic scenario — fake `config.json`/`train_log.jsonl` files for four adaptive runs, a fake baseline-shaped config with no `target_avg_layers` field, and a fake run directory with a config but no log yet — and confirmed the script correctly picked up exactly the four real ones, skipped the other two without crashing, and sorted them correctly. That's what let me trust it on the real sweep rather than debugging it live against ~15 hours of real Kaggle data.

**Q: You mentioned catching an issue in your own code this session — what was it, and why did you remove it rather than leave it?**

But that run is done and won't be re-run — the special case had no actual use, it just made the code harder to read for no benefit. Removed it in favor of one consistent naming rule for every target value. Small thing, but it's the same "don't add complexity beyond what's needed" standard I've been applying when reviewing the surrounding code, applied to something I'd just written myself.

## Session 7 — 2026-09-03

**Q: Walk me through your central result — the accuracy-vs-average-layers curve. What does it show, and how confident are you in it?**
A: Four training runs, identical except for one swept variable (`target_avg_layers` ∈ {2, 4, 6, 9}), same seed and everything else fixed. The result: val loss goes 3.8915 → 3.8423 → 3.8135 → 3.7988 as achieved average depth goes roughly 2.6 → 4.2 → 6.1 → 9.0 — a clean, monotonic diminishing-returns curve, matching the theoretical expectation that most tokens don't need full depth and the biggest quality wins come from giving the hardest tokens just a *little* more room, not from uniformly adding depth everywhere. Confidence: high on the qualitative shape — the largest gap (2→4 layers: 0.0492 loss) is well clear of noise. Lower on the precise magnitude at the flat end — the smallest gap (6→9: 0.0147) is close to the ~0.04 peak-to-peak fluctuation I measured in a single run's own late-training checkpoints, so I'd state that gap as "small, consistent with diminishing returns" rather than a precise number, and I'd want repeated seeds before treating it as pinned down.

**Q: With only one run per sweep point, how do you know the differences you're seeing are real and not just noise from a lucky/unlucky seed?**
A: Honestly, for the small gaps at the shallow end of the curve, I can't fully rule that out with the data I have — that's a real limitation of a single-seed sweep, and I said so rather than overclaiming. What I *can* say: I estimated a noise floor directly from the data already on hand — how much `val_lm` swings across a single run's own last 10 eval checkpoints (~500 steps apart, model already converged) — and the two largest gaps in the curve are clearly bigger than that floor, so those are very likely real signal. The smallest gap is roughly the same size as that floor, so I'm explicit that it's suggestive, not proven, without repeated seeds. That's a more honest and more useful answer than either dismissing the whole curve or overclaiming precision I don't have.

**Q: Why does normalizing the loss deltas by the spacing between points matter here, and which way did it move your conclusion?**
A: The four target values aren't evenly spaced in the depth they actually achieved (2.6→4.2 is a gap of 1.6 layers, but 6.1→9.0 is a gap of 2.9 layers), so comparing raw loss deltas alone slightly conflates "returns are diminishing" with "the last interval just covers more ground." Normalizing to loss-per-additional-layer turned out to make the diminishing-returns pattern look *even sharper*, not weaker — so in this case the correction reinforced the finding rather than undermining it. I checked it because I wanted to know which way it cut before either citing the raw numbers or explaining them away, not because I assumed it would help my case.

**Q: Given real time/compute constraints, how did you prioritize the remaining deliverables — router ablation, real wall-clock speedup, and the token-level visualization?**
A: I ranked them by cost against value rather than treating them as an unordered checklist. Visualization first: it needs no new training at all — just inference with a checkpoint that already exists locally — and it's explicitly the most compelling artifact for communicating what the model actually learned. Router ablation next: moderate cost (a couple more ~5-hour training runs), but the router interface was deliberately designed back when the learned-gate router was first built specifically so alternate router policies could drop in without touching the model's skip mechanics — so the engineering lift is smaller than it sounds. Real hard-skip for wall-clock speedup last: it's the highest-risk, most open-ended engineering piece (dynamic per-token compute shapes aren't trivial to get right in PyTorch), and it's better informed *after* the ablation tells us which router design is actually worth hardening into real sparse compute, rather than betting that engineering effort on whichever router happened to be built first.

**Q: You said the router interface was already designed to be swappable — did it actually cover the two new router types cleanly, or was that an overstatement?**
A: Partly an overstatement, and I said so directly when it came up rather than let the plan imply otherwise. The `forward(x) -> gate` contract from when the learned-gate router was first built did help — both new routers still fit the same "produce a per-token gate" concept. But `FixedTopKRouter` needed a fundamentally different *kind* of decision — ranking across an entire sequence, not a per-token independent function — which nothing in the original interface anticipated. And `ConfidenceThresholdRouter` needed information — the block's own output, not just its input — that the original signature didn't carry at all. Both were still small, well-scoped changes (a factory function keyed on a new config field; one signature extension shared by all three routers), but pretending the original design already solved them would have hidden real complexity from the planning conversation instead of surfacing it where it could actually be discussed.

**Q: The Mixture-of-Depths router selects tokens for processing — how did you handle the fact that "selected" doesn't mean "gets full weight"?**
A: MoD's actual mechanism scales a selected token's contribution by its own learned score, not a flat 1 — that's deliberate, because top-k selection itself isn't differentiable, so scaling by the score is what gives the scorer any gradient at all. I implemented that faithfully rather than simplifying it away, which has a real consequence: the "average depth" metric used everywhere else in the project stops meaning "how many layers this token actually went through" for this router type specifically — it becomes weighted by whatever the score happens to be. I demonstrated that concretely rather than just describing it: at 50% capacity on a 3-layer model, the true selection fraction was exactly 0.5 as designed, but the reported avg_depth came out to 0.75, not the naive 1.5 you'd expect if selected meant full weight. Rather than force one number to mean two different things, I added a second, genuinely exact metric — the true selection fraction — logged alongside it.

**Q: Why does the confidence-threshold router use a relative delta rather than an absolute one, and how did you verify that choice actually mattered?**
A: In a pre-LN transformer, nothing renormalizes the residual stream between blocks, so its magnitude tends to grow across layers — a well-known property of that architecture family. An absolute threshold on "how much did this block change the token" would then be measuring depth, not difficulty: early layers would rarely trip a threshold calibrated for late layers' larger absolute changes, or the reverse, regardless of which tokens were actually hard. Dividing by the token's own current magnitude makes the comparison meaningful at every layer instead. I didn't just reason about this and move on — I wrote a direct test: the same relative displacement at very different absolute magnitudes (‖x‖=1 versus ‖x‖=50) produces the identical gate decision, which is the property the whole design depends on.

**Q: Before spending real Kaggle GPU-hours on the confidence-threshold run, how did you pick the threshold value?**
A: I didn't want the first real attempt to just be a guess, so I built a small local calibration script that measures what the *actual* architecture — same 12 layers, same 384 dimensions as the real training run — actually produces on *real* WikiText-103 validation data, using a freshly-initialized, untrained model (reasonable as a starting point specifically because nothing's been trained yet, so there's no learned feedback loop between layers to account for). That takes seconds locally and needs no GPU. The placeholder default I'd been using, 0.1, turned out to be badly wrong — it selected essentially every token. The empirically measured value, about 0.43, was designed to land near an average depth of 6, matching the other two ablation arms. I then validated that estimate against the real routing forward pass, not just the calibration measurement, and it came out close (6.43 versus a target of 6) — with an honest, explicable gap, since real routing lets an early-frozen token change what later layers see in a way the calibration's simplified bypass measurement doesn't capture.

## Session 9 — 2026-09-07

**Q: Your `ablation_topk` run's log file had 59 rows for what should have been a 41-checkpoint run — what did that actually mean, and how did you find it?**
A: It meant the file wasn't the output of one continuous run — it was two separate Kaggle executions that both happened to append to the same `train_log.jsonl` path. I caught it by not stopping at "does the last row look right" (it did: step 20000, sane loss). Instead I compared the count of log rows to the count of *unique* step numbers — 59 vs. 41 — which immediately said something was duplicated. Then I looked at the `elapsed_s` field per row: it climbs steadily from ~74s up through step 8500, then drops back down to ~60s at a *second* `step: 0` entry, and climbs steadily again all the way to step 20000. A monotonic wall-clock counter resetting mid-sequence is the signature of a new process starting from scratch, not the same process resuming — so the story is: a first attempt ran to about step 8500 and stopped, and a second, successful attempt was later launched and appended straight into the same log file instead of a fresh one.

**Q: Did that log anomaly invalidate the `ablation_topk` result?**
A: No — the final checkpoint and the final logged row both came from the second, complete run (step 20000, matching the config's `max_steps`), so the numbers I used are legitimate. What it does invalidate is any *full-curve* plot built naively from that file — the first ~8500 steps would show a sawtooth (loss dropping, then jumping back up) that isn't real training instability, it's two different runs' early training interleaved. Since `plot_ablation.py` only reads each run's final record rather than the whole trajectory, it was unaffected — but I logged the anomaly explicitly rather than quietly ignoring it, since anyone plotting this run's curve later needs to know to de-duplicate by step first.

**Q: How do you compare a fixed top-k router against a learned gate router when they don't log the same depth metric?**
A: They don't share a native metric, but they do share what that metric is a proxy for: fraction of total available compute actually used. `fixed_topk` logs `nonzero_frac` — the exact fraction of tokens selected at each layer, which is a hard constraint by construction. `learned_gate` logs `avg_depth` — the average number of effective layers a token receives, out of `n_layer` total. Dividing `avg_depth` by `n_layer` converts it into the same "fraction of full depth used" units as `nonzero_frac`. In this case that landed the two runs almost exactly on the same effective budget (0.507 vs. 0.5), which made a same-compute comparison possible: at that matched budget, the learned gate reached a meaningfully lower validation loss than fixed top-k (3.8135 vs. 3.9139). That's a real, interesting early ablation signal — though it's only one of two ablation arms, so I was careful to call it preliminary rather than a final verdict on which router design wins.

## Session 10 — 2026-09-08

**Q: You now have all three router ablation arms complete — which one wins, and why?**
A: The end-to-end learned gate wins clearly: val_lm 3.8135 at avg_depth 6.08, versus fixed top-k's 3.9139 at nonzero_frac 0.5 and confidence-threshold's 4.0682 at nonzero_frac 0.255. The "why" is the more interesting part: the learned gate is the only router whose selection mechanism co-adapts with the base model during training — a budget-loss gradient continuously pushes its behavior back toward the target as the model's internal representations change. The two static routers were each calibrated or fixed once and then held constant; one of them visibly went stale as a result. So the result isn't just "the learned approach happens to score better," it's "the learned approach is robust to a specific failure mode the static approaches aren't."

**Q: You said none of the three routers actually landed at the same compute budget, even though all three targeted avg_depth≈6 — how did that happen, and does it undermine the ablation?**
A: It happened because two of the three routers can't respond to how training changes the model, and one drifted badly as a result. `fixed_topk` is exactly 50% selection by construction — a rank-based rule, so it's immune to this regardless of how token scores are distributed. `confidence_threshold` is a magnitude-based rule: its threshold (0.4309) was empirically calibrated in an earlier session against an *untrained*, randomly-initialized model to hit avg_depth≈6.4. Once real training happened, the model's layer-to-layer representations apparently stabilize (smaller relative change per block) much more than an untrained model's do — so the same fixed threshold let far more tokens exit early than intended, and the achieved budget fell to nonzero_frac 0.255 (avg_depth 3.06), roughly half the target. It doesn't undermine the ablation — if anything it strengthens it, because it's direct evidence for *why* a jointly-trained router generalizes better: it can track a moving target that a router calibrated once, offline, cannot.

**Q: Doesn't it seem unfair that confidence-threshold ran at a lower compute budget than the other two and still lost — maybe it would win if you fixed the budget mismatch?**
A: I checked that specifically rather than assuming it either way. If anything, running at a lower budget should have made confidence-threshold's job *easier* — using less compute is normally the "cheap and worse" side of a quality/compute tradeoff, and its worse loss would be expected then. But it's not winning on the compute side either: `fixed_topk` uses almost exactly double the compute (nonzero_frac 0.5 vs. 0.255) for a lower loss, so confidence-threshold isn't trading quality for efficiency — it's simply dominated on both axes by fixed top-k, and dominated on quality alone by learned-gate at a similar budget to fixed-topk. A budget-matched rerun could still be worth doing for rigor, but the current evidence doesn't suggest confidence-threshold is being penalized unfairly by the mismatch — it's underperforming even where it should have the efficiency advantage.

**Q: What's the practical takeaway from this ablation for choosing a router design in a real system?**
A: If you can afford to train the router jointly with the model (and eat the extra training-time cost/complexity of the budget-loss term), it's worth it — this ablation shows a real, non-trivial quality gap in its favor, not just parity. If you need a hard, guaranteed compute ceiling for deployment (an SLA-style constraint that must never be violated regardless of input), fixed top-k is the safer static choice specifically because its guarantee is rank-based and doesn't degrade as the model or its inputs drift. A fixed confidence/magnitude threshold is the one I'd be most cautious about shipping without periodic re-calibration — this ablation is direct evidence that its effective behavior can silently drift away from its intended operating point as the underlying model changes, with no mechanism to self-correct.

**Q: You built real hard-skip for `learned_gate` first, since it won the ablation — what happened, and why did you end up benchmarking `fixed_topk` instead?**
A: Real hard-skip on `learned_gate` catastrophically broke quality — val_lm nearly doubled at the real capacity. I didn't stop at "it's bad," I traced it to two separate causes. First, excluding tokens from attention entirely (the literal Mixture-of-Depths mechanism) assumes a model trained to expect that exclusion; `learned_gate` was trained with attention always fully dense for every token, so removing a token from the K/V pool broke something the model genuinely relied on. I fixed that (kept attention dense, only skipped the MLP for excluded tokens) and it helped, but not enough — val_lm was still nearly double dense. So I inspected the actual trained gate distribution directly rather than guessing further, and found it's broad and centered around 0.5, not sparse — the router's budget loss only ever pushes the population *average* toward the target, never individual scores toward 0 or 1, so there's no rank cutoff where "treat as zero" is a safe approximation. That's a property of what the router learned, not of the masking mechanism. Given that, I tested the exact same unmodified code against `fixed_topk`'s checkpoint instead, since its router was already trained with real top-k masking (exact zero for non-selected tokens, every forward pass, during training itself) — and it worked essentially perfectly, matching dense output to four decimal places on every real validation batch tested.

**Q: Doesn't pivoting away from the ablation's own quality winner undercut the ablation's conclusion?**
A: No — it adds a second, independent dimension to it rather than contradicting the first. The ablation answered "which router generalizes best under its own soft training objective" (learned_gate, clearly). This is a different question: "which router's training-time behavior is structurally compatible with a real, hard, post-hoc compute-skipping mechanism" (fixed_topk, clearly, and for a specific, well-understood reason — its masking was never approximate to begin with). Both are true and both are useful — the practical lesson is that soft-training quality and hard-deployment compatibility are separate axes that don't automatically move together, and a real system should check both before committing to a router design based on offline quality metrics alone.

**Q: What was the actual real-GPU wall-clock result, and is it good?**
A: At the real batch/sequence shape (32×256, matching training), eager mode: baseline 195.21ms, the dense Phase-1 adaptive model 214.84ms, and real hard-skip 190.53ms. So hard-skip is 11.3% faster than the fair comparison point (the same model, same router, dense compute path) and about 2.4% faster than the plain static baseline. Whether that's "good" depends on what you compare it to. Against the naive expectation ("we skip compute for ~50% of tokens, so ~50% faster"), it looks disappointing. But that's the wrong ceiling — the mechanism that actually preserves quality only skips the MLP sub-layer, never attention, and a FLOPs breakdown of this exact architecture shows MLP is only about 70% of a block's compute. So the honest theoretical ceiling is closer to 35%, not 50%. Against that more precise number, 11.3% is still a real gap, but a much more explainable one, and it's a genuine, confirmed, non-fabricated speedup measured on real GPU hardware — not noise, and not a rounding artifact (it holds up on both directly-computed backends I compared).

**Q: Where does the remaining gap between the ~35% theoretical ceiling and the ~11% real result likely come from?**
A: Three plausible, nameable causes, though I didn't run a full profiler to apportion them precisely (a good next step, not something I'd claim to have already measured exactly). First, gather/scatter — the operations that actually implement "only compute this subset of tokens" — are memory-bound, irregular-access operations on GPU; they cost real time that eats into whatever compute was saved. Second, this is a small model (about 15M parameters) at a modest batch/sequence size, so the dense matmuls being compared against may not fully saturate the GPU's compute capacity to begin with — when you're not compute-bound, cutting FLOPs doesn't cut wall-clock time proportionally. Third, `torch.compile` — whose main benefit is fusing kernels to reduce overhead in compute-bound workloads — gave no consistent benefit anywhere in this benchmark, and even made hard-skip's compiled variant 3.3% slower than its eager version, plausibly because compile/Triton doesn't optimize dynamic-shape gather-based execution as well as static dense matmuls.

**Q: `torch.compile` didn't help, and even hurt in one case — doesn't that undermine the benchmark?**
A: No — it's a legitimate, reportable finding in its own right, and it's exactly the kind of result the project explicitly wanted documented ("the gap between theoretical and real speedup"). I checked all three variants, both eager and compiled, at the real GPU shape: baseline got 1.8% slower compiled, dense adaptive got 1.8% faster, and hard-skip got 3.34% slower. That's not a systematic "compile always helps a bit" pattern — it's closer to noise-level with one clear exception (hard-skip getting worse), which is consistent with compile struggling specifically with the dynamic gather/scatter operations hard-skip introduces. Reporting "compile gave no consistent benefit, and may specifically conflict with hard-skip's control flow" is a more honest and more interesting finding than a single averaged "compile: +0%" would have been.

## Project completion audit — 2026-09-08

Before calling the project done, I re-read every `.md` file cold and cross-checked specific claims against the actual filesystem and source code — not just re-summarized what the logs already said. This surfaced real findings, documented below both ways: what genuinely succeeded, and where the evidence is thinner than the running summaries suggested.

**Q: Did this project actually prove what it set out to prove — that a model can learn to allocate compute unevenly per token and get comparable quality for less real-world work?**
A: Partially, and more narrowly than "the definition of done is complete" makes it sound. Every individual piece of evidence is real and independently verified — I re-checked each one against actual files, not against prior summaries, during this audit. But the two halves of the hypothesis (comparable quality; less *real-world* work) were never demonstrated on the same router or checkpoint. The accuracy-vs-avg-layers curve — the evidence that quality holds up well across a wide range of compute budgets — was built entirely with `learned_gate` running in Phase 1's soft mode, which by construction achieves zero real wall-clock savings (every token still computes through every layer; only the residual update is scaled). The real, measured 11.3% wall-clock speedup was only ever demonstrated for a different router, `fixed_topk`, at one single fixed budget — and `fixed_topk`'s own quality is measurably worse than `learned_gate`'s. So: heterogeneous compute allocation that preserves quality is real and well-evidenced; real wall-clock savings from that allocation is also real and well-evidenced; but they're two separate experiments, not one continuous proof.

**Q: Why weren't they the same experiment — why not just hard-skip the model that already proved quality preservation?**
A: I tried that first, actually — it's not an oversight, it's a real result. Real hard-skip on `learned_gate` (the router the accuracy curve was built with) collapsed quality, because its trained gate scores turned out to be broadly distributed rather than sparse — there's no rank-based cutoff that safely approximates "excluded" tokens as contributing zero. That's a genuine, mechanistic finding about *why* the two halves don't compose for free: a router optimized to preserve quality under a *soft*, continuous training signal has no reason to also produce a distribution that's friendly to a *hard*, discrete cutoff at inference. The router that does support hard-skip cleanly (`fixed_topk`) does so because its masking was already hard and exact during training — a structural property, not a coincidence — but that same structural constraint is very likely part of why it scores worse on quality in the first place.

**Q: If you had to say exactly what is proven versus what isn't, how would you draw that line?**
A: Proven, with real verified numbers: (1) a jointly-trained router can allocate a controllable, non-uniform amount of computation per token and the resulting quality degrades smoothly and only modestly as the average budget shrinks (the sweep, single-seed, largest gaps well clear of the measured noise floor); (2) three different router designs produce measurably different quality at nominally the same budget, for mechanistically understood reasons (the ablation); (3) at least one router design (`fixed_topk`) can be converted to real, hard, compute-skipping inference with an exactly verified zero quality cost relative to its own dense forward pass; (4) that real hard-skip produces a real, measured 11.3% wall-clock speedup on GPU hardware, not a simulated or theoretical one. Not proven: that the *best* router can be hard-skipped at all without retraining; a real wall-clock speedup at more than one operating point; any of this against a precisely known static-baseline number (the baseline's exact final loss was lost — genuinely lost, not just unreported, and I found during this audit that an earlier session's claim that it survived was actually wrong); and why the real speedup (11.3%) falls as far short as it does of even the mechanism's own honest FLOPs ceiling (35.3%) — three plausible causes are named, none confirmed with a profiler.

**Q: You said an earlier log entry was factually wrong — what happened, and how did you catch it?**
A: `memory.md`'s Session 4 entry states the baseline run's `train_log.jsonl` and `config.json` "survived (already saved separately)" after the checkpoint was lost to a Colab disconnect. During this audit I didn't take that at face value — I ran a direct directory listing and a repo-wide search for any file mentioning `baseline_v1`. Neither the config nor the log exists anywhere in the repository; only the rendered chart image does. That claim was simply wrong, and every later reference to "the baseline's numbers" that built on it was actually referencing a chart image, not a number. I corrected the entry in place rather than leaving it standing, and traced the actual consequence forward: this project has never had a precise, citable baseline loss value, which is why every "adaptive is comparable to baseline" statement in this project has been a visual approximation, not an exact comparison.

**Q: Given all that, would you call this project a success?**
A: Yes, as a research and engineering exercise — with the caveat stated plainly rather than glossed over. The individual findings are real, mostly non-obvious, and each one was arrived at by actually testing something rather than assuming it (the attention-exclusion failure, the gate-sparsity root cause, the FLOPs-ceiling calculation, the baseline-files discrepancy this audit itself found). That process — building a claim, testing it hard, finding it doesn't fully hold, tracing the actual reason, and adjusting scope honestly rather than quietly — is arguably the more interesting interview story than a clean, unified "it worked exactly as hypothesized" result would have been. But it would be overselling to call the core hypothesis fully proven end-to-end. It's proven in pieces, with an honestly-identified seam in the middle where the pieces don't yet connect.

**Q: What would it take to close that gap, concretely?**
A: Three things, in order of leverage: (1) get a real, precise baseline number — either retrain `baseline_v1` (known-cheap now that the pipeline is debugged) or accept the loss as permanent but state it explicitly rather than let "visually similar" stand in for it; (2) get one router to demonstrate both halves at once — either fine-tune `learned_gate` toward a sparser score distribution so it can be hard-skipped too, or treat `fixed_topk` as the deployable design and sweep its own `topk_capacity` the way `target_avg_layers` was swept for `learned_gate`, producing a real accuracy-vs-*achieved-wall-clock* curve instead of one point; (3) profile the 35.3%→11.3% gap instead of naming plausible causes for it. None of these are large efforts relative to what's already built — the infrastructure (sweep methodology, benchmark harness, hard-skip machinery) all already exists and would be reused as-is.

## Session 11 — 2026-09-09

**Q: Before committing ~15 Kaggle-hours to retraining `fixed_topk` at new capacities, you built a cheaper diagnostic first — what did it show, and how much do you trust it?**
A: I tested whether the already-trained capacity=0.5 checkpoint could just be run at other capacities at inference time, no retraining needed — a real, meaningful shortcut if it worked. It didn't, decisively: at capacity 0.1667 the loss came out *worse than uniform-random guessing* over the vocabulary, and even the wider direction (0.75, which I expected might be safe on the theory that extra compute is never harmful for next-token prediction) showed a real, non-trivial cost. That's not a marginal or ambiguous result — it's a clean, bidirectional collapse, which told me this is a property of how the base model's weights specialize to a specific training-time token density, not something a cheaper workaround could route around. I trust the conclusion because the diagnostic itself was validated first: it has to reproduce the already-proven exact `+0.0000` match at capacity=0.5 before any off-capacity number from it means anything, and it does.

**Q: You mentioned catching a bug in the diagnostic itself — what was it?**
A: The diagnostic needs to test capacities the router wasn't built with, which means bypassing its normal forward pass (which only knows its own trained capacity) and pulling the raw score straight from its scoring network. My first version did that but forgot that the router's real forward pass also *zeroes* the score for every token it doesn't select, before that score is used anywhere downstream — I was leaving excluded tokens with a small real score instead of the exact zero the model was actually trained with. That's not a rounding difference, it's a real behavioral gap, and it's exactly why I built in a self-consistency check first: testing the diagnostic at the *trained* capacity (0.5) must reproduce the already-proven exact result, and it didn't (+0.083 instead of +0.0000) until I fixed the masking. Without that check, I could easily have shipped off-capacity numbers that were systematically wrong in a way that looked plausible.

**Q: Separately, your notebook-verification harness had its own bugs — what happened, and what's the actual lesson?**
A: Two bugs, both revealing the same underlying pattern. I inject a tiny/fast architecture and a specific router type into the code I'm testing by placing values into the execution namespace *before* running it — but the actual cell text I'm testing contains its own `from config import AdaptiveConfig` import and its own hardcoded `ROUTER_TYPE = "learned_gate"` assignment, and both of those silently overwrote what I'd placed there. The first one looked like a hang — it wasn't; it was a real, full-scale ~40-million-parameter model actually training on CPU, which I caught by reading the printed parameter count rather than waiting it out. The second one is the more interesting failure: my own assertions all passed, because they checked a dictionary's literal contents, which were genuinely correct — they just didn't check what the code actually *did* with that dictionary, which had already been computed from the wrong, silently-overwritten router type. Only reading the full log output — not the pass/fail summary — showed every run printing the wrong run name. The lesson: an injected default and a hardcoded line with the same name will conflict, and the executed code's own assignment always wins; the fix is to edit the literal text (simulating the real one-line edit a user would make), not to pre-load the namespace and hope it survives.

**Q: Doesn't finding two bugs in your own verification process undermine confidence in Module 2's actual result?**
A: The opposite, if the bugs are found and fixed rather than shipped. Both were caught specifically *because* the verification bar was strict — a byte-identity check, a real execution of the actual cell text (not a description of it), and a self-consistency requirement that has to hold exactly, not approximately. A weaker verification approach (eyeball the diff, assume the assertions are checking the right thing) would have missed both and reported a false pass. The fact that the process caught its own mistakes before they reached a conclusion is the verification discipline working as intended, not a sign it's unreliable.

## Session 12 — 2026-09-10

**Q: How did you verify three brand-new training runs before trusting any of their numbers?**
A: The exact same protocol used for every prior run in this project, applied unconditionally rather than only when something looked suspicious: each run's `config.json` had to match its intended sweep point exactly — router type, capacity, and every other hyperparameter identical to every other run in the project, nothing silently different. Each `train_log.jsonl` had to pass the same anomaly checks that caught a real duplicate-run artifact in an earlier run — line count equal to unique step count, the step sequence matching the expected `0` to `20000` by `500` exactly, and elapsed time strictly increasing throughout (which rules out a restarted run silently appended to the same file). And each checkpoint's file size had to match the known-good value for this exact architecture. All three passed clean on every check.

**Q: The achieved `nonzero_frac` wasn't exactly equal to the configured `topk_capacity` — is that a problem?**
A: No, and I checked why rather than just assuming it was harmless rounding. `FixedTopKRouter` selects `round(capacity × block_size)` tokens per sequence — at `block_size=256`, a capacity of `0.1667` rounds to exactly 43 tokens, and `43/256 = 0.1680`, which is precisely what got logged. It's a fully explained, expected artifact of converting a fractional capacity into a whole number of tokens, not a training anomaly — worth confirming the exact mechanism rather than either dismissing the mismatch or treating it as something requiring further investigation.

**Q: Now that you have all four points of `fixed_topk`'s own capacity sweep, what does the shape tell you?**
A: The same qualitative diminishing-returns pattern as the original `learned_gate` sweep — val_lm drops from 4.27 at capacity 0.1667 to 3.86 at capacity 0.75, with the biggest quality jump at the low end (0.1667→0.3333: -0.25) and progressively smaller gains as capacity increases (0.5→0.75: -0.06). That's a useful cross-check in its own right, beyond just being one more curve: two structurally different routers, trained completely independently, both show the same shape — which is evidence the "most tokens don't need full computation" finding reflects something real about the task, not an artifact specific to one router's particular training dynamics.

## Session 13 — 2026-09-10

**Q: You now have real speedup numbers at four capacities instead of one — what do they actually show?**
A: A clean, monotonic tradeoff: 27.51% faster than dense at capacity 0.1667, 22.12% at 0.3333, 17.05% at 0.5, 6.12% at 0.75 — shrinking exactly as you'd expect, since a higher capacity means fewer tokens get skipped, so there's less to save. I didn't just trust the ratios — I checked the underlying consistency claim first: `baseline` and `adaptive_dense` (both architecturally incapable of depending on capacity) came back essentially flat across all four points (3.26% and 5.22% range respectively, consistent with ordinary GPU timing noise), while `adaptive_hard_skip` showed a real 41ms, strictly monotonic trend. That's not just "the numbers look like a trend" — it's a direct empirical confirmation that the *only* thing driving the change is the thing that's supposed to be driving it.

**Q: You found a discrepancy between this run and an earlier one at the same capacity — why didn't that undermine the result?**
A: Because it's a difference in precision, not in kind. This sweep's capacity=0.5 point showed a 17.05% speedup; an earlier, separately-reported single-capacity benchmark (different Kaggle session) showed 11.31% at the same nominal capacity. Both runs agree on the thing that actually matters — hard-skip is reliably faster than dense, and increasingly so at lower capacity — they just disagree on the exact percentage by about 6 points, almost certainly from ordinary GPU-instance or session-level variance rather than anything about the model changing. I handled it the way I'd want a real research finding handled: reported both numbers, named the likely cause instead of picking whichever one looked better, and made sure the final chart uses only one internally-consistent session's data rather than silently blending two sessions with different absolute latencies into one curve.

**Q: You said Path A closes the gap the earlier audit found — walk me through exactly what changed.**
A: The audit's core complaint was that the "quality holds up" evidence and the "real speedup is real" evidence lived on two different routers and were never joined. Path A fixes that directly: I verified hard-skip's exact-reproduction property at three *new* capacities, not just the one already tested, confirming the "excluded tokens contribute exactly zero" property is a general fact about how `fixed_topk` was trained, not a coincidence at one setting. Then I got real Kaggle GPU numbers at all four of those same capacities. So now there's one router, four independently-trained checkpoints, four real measured latencies, and a proven-lossless hard-skip path connecting them — accuracy and real speed on the same object, at four points, not one router's accuracy and a different router's speed.

**Q: Does this mean the project's core hypothesis is now fully, unconditionally proven?**
A: Close, but I want to be precise rather than declare total victory. The specific gap the audit identified — quality and speed evidence never unified on one router — is genuinely closed now, with real data. What's *not* closed, because it was never in Path A's scope, is that the original static baseline's exact quality number is still lost (confirmed again this session — `experiments/baseline_v1/` still doesn't exist) — so "comparable to the untouched baseline" specifically still rests on an approximate, chart-read number, not an exact one. That's a narrower, less central claim than the one Path A fixed, and it doesn't undermine the core internal finding (a router can trade real quality for real, measured speed, verified end-to-end), but it would be dishonest to say every open question is closed. I'd call the verdict now "the core hypothesis is proven, with one small, pre-existing, clearly-scoped caveat" rather than "fully complete with zero caveats."

**Q: If someone pushed back and asked "why should I trust a benchmark that gave two different answers for the same thing," what would you say?**
A: I'd say that's exactly the right thing to be suspicious of, and it's also why I reported it instead of hiding it. A benchmark that always gives the identical number run after run, on shared cloud GPU infrastructure, would actually be more suspicious — real hardware has real variance. What matters is whether the *qualitative* claim holds under that variance, and it does: in both sessions, at every capacity tested in both, hard-skip was faster than dense, and the relationship between capacity and speedup was in the same direction. The exact percentage moving by a few points between sessions is normal measurement noise on a real system; a "fully proven" claim in this project has always meant "verified with real evidence, discrepancies included," not "produces a single unchanging number regardless of when you run it."
